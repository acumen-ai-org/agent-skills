# Release 2026.06.20.1 — Report A vs Report B

Two HTML reports present the same release of Captario SUM (2026.06.20.1: 76 commits cut from `qa-staging` at `1d60aafb6` on 2026-06-23, 13 analysis fragments across 8 categories, rollup 2 ok / 1 info / 5 warn / 5 error).

- **Report A** — `test/original/2026.06.20.1/`: a release-report *folder* produced by the dev-reporting system: `index.html` (116,058,913 bytes) plus a `data/` tree of 14 JSON files (manifest + 13 fragments, ~38 MB) and references to `assets/app.css` / `assets/app.js`. The full original folder unpacks to ~224 MB; the subset inspected here is ~149 MB.
- **Report B** — `claudedocs/release-2026.06.20.1-report.html`: a *single* self-contained HTML file (39,583 bytes) generated by the `report-compose` skill from a hand-authored spec (`report.json` + 14 unit HTML files + `charts.js`).

The size ratio is roughly 2,900:1 (116 MB vs 39 KB). The sections below describe what differs.

## Packaging and architecture

A is a folder-shaped application: `index.html` is a thin shell (48 lines of markup) whose weight is a single `<script id="report-data" type="application/json">` blob of 116,056,821 bytes — 99.998% of the file — containing 57 JSON documents. The shell references external `assets/app.css` and `assets/app.js`; app.js is the rendering engine that reads the blob and builds the entire UI at runtime, and the same fragment JSONs also exist as separate files under `data/` (e.g. `data/report/release-diff.json`, 22.5 MB). B is one 950-line HTML file with all CSS (~360 lines) and all JS (~420 lines) inlined; there are no companion files and no runtime data payload — the 14 content sections are pre-rendered static HTML in the body.

> WHY: report-compose's output contract is one self-contained .html that opens via file:// anywhere — its validator rejects every relative reference, so companion asset or data files are impossible by construction. Content is pre-rendered because the skill's content role writes finished HTML units at authoring time; there is no runtime data payload to render from.

## Data-driven renderer vs authored document

A's content is not authored HTML at all: each fragment conforms to the `dev-report-fragment/v1` schema, whose typed body blocks (`metric-cards`, `table` with sortable/filterable columns and nested `children` rows, `markdown`, `d3-graph`, `treemap`, `heatmap`, `key-value`, `image`, `diff-view`, `link`) are interpreted by app.js into UI. B inverts this: an authored spec of 14 small HTML units (350–770 bytes each) was compiled once into the final page; the JSON fragments were the *input to authoring*, not something the page carries. Consequently A can re-render anything in its payload; B shows exactly and only what was written into its units.

> WHY: the skill's pipeline is a content role that reads input and writes prose, then a structure role that splices those units into the template mechanically. The template's engine handles presentation (modes, navigation, control enhancement), not data interpretation — a fragment-schema renderer like app.js has no place in that division of labor.

## Data completeness and granularity

A carries the full analysis payloads: about **35,250 table rows** across the 13 fragments (28,182 in the TrueCourse code-health review, 2,912 in repository evolution, 2,161 in the architecture source scan, 915 TrueCourse architecture findings, 409 security rows, 383 schema-diff rows, 151 supply-chain rows including per-CVE child rows, 121 author-activity rows), each with per-finding detail down to file, line, severity, and message. B compresses all of that into headline numbers: its only data table has **6 rows** (PR kinds), and the rest is stat tiles, key-value lists, and callouts — e.g. "28,182 findings" as one sentence where A holds 28,182 individually listed findings, and "114 unique vulnerable dependency findings" as a chart caption where A lists every library and CVE. The one per-finding detail B preserves verbatim is the single semgrep warning (`js-open-redirect` at `login.js:73`), because there was only one.

> WHY: the skill's density rule sizes every unit for a slide/panel (one idea, ~6 bullets or one ~6-row table), and its inventory step instructs the content role to list what the reader would miss and surface headline facts — the fragments were treated as source material to summarize, not payloads to embed. The single semgrep finding survived verbatim precisely because it fit inside one callout.

## Previous-release history

A embeds not just the current release but the data of **8 previous releases** (2026.06.02.1 through 2026.06.11.2) plus a `releases.json` index — roughly 60 MB of the 116 MB blob is prior-release fragments (the 2026.06.02.1 release-diff alone is 35.5 MB). This feeds a "Show/hide previous releases" split-screen: a `#pane-current` / `#pane-previous` two-pane layout with previous-release controls. B has no historical data at all; it covers the single release and offers no comparison to earlier ones.

> WHY: the generation input was this release's fragment set only; the spec format has no concept of release history, and prev/next comparison belongs to the dev-reporting system's releases.json machinery, which was never part of the authored spec.

## Navigation and viewing model

A's UI (from `index.html` markup plus `assets/app.js`) is a sidebar application: a release header, a category-based nav built from the manifest, a **module filter** select over the 10 modules listed in the manifest (`root`, `core`, `foundation`, `modules/ai` … `tools`), the previous-releases split toggle, and a **file modal** for inspecting individual file contents/diffs. B has no filters or modals; instead it ships **three viewing modes** switched by a fixed pill control: *Full* (scrolling document with sticky sidebar, area tabs, and scroll-spy), *Slides* (keyboard/click-driven deck with progress bar and slide counter), and *XR* (scroll-snap full-viewport panels with a dot rail). B also auto-generates **gateway** sections between its areas (Release / Analysis / Report) and categories, acting as in-page tables of contents; A has nothing equivalent.

> WHY: modes, area tabs, and gateways are what the report-compose template engine provides — every output inherits them verbatim because the engine ships unchanged in each file. A module filter or file modal does not exist in the skill's controls registry, so no output can carry one.

## Content A shows that B does not

Beyond the raw finding tables, A carries: **five base64-embedded PNG illustrations** (~5.3–6.0 MB each: one in the overview, four in the release-diff perspectives — ~28 MB of data URIs total); **nine d3 dependency graphs**, a treemap, and a heatmap in the architecture/evolution fragments; a multi-perspective **diff-view** block; per-fragment **help documents** (markdown explaining how to read each fragment); per-fragment producer metadata with `generated_at` timestamps and severity scores; and the Azure DevOps build link from the manifest. None of these appear in B — B has no images, no graphs beyond one bar chart, no diff rendering, no help texts.

> WHY: the controls registry bounds what an output can render (Plot charts, Mermaid, side-by-side diffs, Excalidraw, sparklines, tables, tiles); d3 dependency graphs, treemaps, and file modals are not registry controls. The graceful-degradation rule also biases authoring toward stating facts in text and captions rather than in visuals, and the content role selected no images to embed.

## Content B adds that A lacks

B adds interpretive narrative: it states that lines removed (136,818) exceed lines added (131,164) and connects that to the design-refresh consolidation in the published notes; it explains *why* 4 producers were skipped (source-scan fallback because depcruise/madge were not configured, evolution enrichers skipped); and it flags that the release-diff fragment "reports status error with no summary emitted". It renders one **Observable Plot bar chart** of vulnerability severities (A presents the same numbers as metric cards, not a chart). It also adds explicit provenance: a cover line and footer naming the generator (`report-compose`), the generation date (2026-07-22), and the source data, plus a note that the page "remains readable without" its pinned CDN dependencies. Some of B's headline numbers (lines added/removed, attack-surface ingress 360 / egress 36, the PR-kind breakdown) are surfaced from deep inside A's fragments, where they exist but only inside tables.

> WHY: the content role is a language model told to make sense of the input (inventory, structure, then author), so connecting the line-removal balance to the design refresh is the expected product of that step. The provenance line, generator meta, and dependency-listing footer are mandated by the output contract and generated by build_report.py from report.json — they exist in every output regardless of content.

## Interactivity and runtime dependencies

A loads four CDN libraries from jsdelivr with SRI pins — marked 12.0.2 (markdown), DOMPurify 3.1.6 (sanitizing), d3 7.9.0 (graphs/treemap/heatmap), diff 7.0.0 (diff views) — and depends on the non-embedded `assets/app.js` / `assets/app.css` to render anything at all: without app.js the page body is empty scaffolding. Its interactivity is data-centric: sortable/filterable tables with expandable child rows, module filtering, split-screen release comparison, file modal. B loads Google Fonts plus d3 7.9.0 and Observable Plot 0.6.17 (also SRI-pinned) but degrades gracefully — every section is static HTML that renders without JavaScript; scripts only add the mode switching, navigation chrome, and the one chart. B's interactivity is presentation-centric (modes, keyboard slide navigation, scroll-spy), not data exploration.

> WHY: build_report.py includes only the CDN libraries whose controls appear in the authored content — one chart means d3 + Plot and nothing else. No-JS readability is a hard clause of the output contract (facts must survive without the engine), which forces all substance into static HTML and confines scripts to presentation chrome.

## Size and portability

A totals ~224 MB in its full original form (~149 MB in the inspected subset: 111 MB `index.html` + 38 MB `data/`), must travel as a folder, and needs its `assets/` directory intact to function; the large embedded blob also makes the HTML heavy to parse on open. B is a single 39,583-byte file (about 1/2,900th of A's index.html alone) that can be emailed or attached anywhere and opens instantly; both are designed to open via `file://` with no server, and both reach out to CDNs for their libraries, but only A hard-depends on local sibling files.

> WHY: the size is the compound consequence of the design choices above — summarized content instead of embedded payloads, a pruned library set, no history, no images. The single-file constraint deliberately trades data volume for portability; nothing in the pipeline can emit a folder.

## Summary

The two artifacts are different report genres built from the same fragments: A is a data warehouse with a viewer — a folder whose 116 MB index embeds 57 JSON documents (current release, 8 previous releases, ~35,000 finding rows, 28 MB of illustrations) and delegates all rendering to an external app.js that provides tables, filters, graphs, split-screen history, and file modals; B is a 39 KB curated briefing — a single self-contained page that reduces every fragment to headline numbers, one table, and one chart, adds narrative interpretation and provenance that A lacks, and spends its engineering on presentation modes (Full/Slides/XR) rather than data exploration. A preserves everything and lets the reader drill down; B selects, explains, and stays portable.
